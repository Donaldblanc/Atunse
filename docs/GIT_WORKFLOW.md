# Git workflow (git-flow)

This repo uses git-flow. Nothing lands on `main` except through a
`release/*` or `hotfix/*` branch, enforced by branch protection plus the
`Branch guard` required check — not just convention.

## Branches

| Branch | Purpose | Protected | Merges into |
|---|---|---|---|
| `main` | Production history. Every commit here is a shipped release, tagged `vX.Y.Z`. | Yes | — |
| `develop` | Integration branch. Default branch — this is what you branch features from. | Yes | `main` (via `release/*`) |
| `feature/*` | One feature/fix/chore. Branch from `develop`. | No | `develop` |
| `release/*` | Stabilizes a batch of `develop` for shipping (version bump, changelog, last-minute fixes only). Branch from `develop`. | No | `main` **and** `develop` |
| `hotfix/*` | Urgent production fix that can't wait for the next release. Branch from `main`. | No | `main` **and** `develop` |

Day-to-day work: branch `feature/<short-name>` off `develop`, PR back into
`develop`. That PR only needs CI green — no approval required (solo
maintainer today), but direct pushes to `develop` are blocked, so every
change is still a reviewable, revertible PR.

## Cutting a release

```bash
git checkout develop
git pull
git checkout -b release/1.2.0
# bump "version" in package.json to 1.2.0
git commit -am "chore: bump version to 1.2.0"
git push -u origin release/1.2.0
```

Open a PR `release/1.2.0` → `main`. `Branch guard` (a required check) fails
the PR if it's opened from anything other than `release/*`/`hotfix/*` — you
cannot accidentally merge a feature branch straight into `main`.

Once merged:
- `Release` workflow reads the new version from `package.json`, tags the
  merge commit `v1.2.0`, and publishes a GitHub Release with autogenerated
  notes.
- It then opens a PR back-merging `main` into `develop`, so `develop` never
  drifts behind a release. Merge that PR once CI passes.

If `package.json`'s version wasn't bumped, the workflow skips tagging
instead of re-tagging an existing version — bump the version as part of the
release branch, not after.

## Hotfixes

Same shape as a release, branched from `main` instead of `develop`:

```bash
git checkout main
git pull
git checkout -b hotfix/1.2.1
# fix the bug, bump version to 1.2.1
git push -u origin hotfix/1.2.1
```

PR `hotfix/1.2.1` → `main`. Same tagging + back-merge-to-develop automation
runs afterward.

## Branch protection (configured on GitHub, not just this doc)

Both `main` and `develop`:
- No direct pushes — every change is a PR
- CI (`test`) must pass before merge
- Branch must be up to date with its base before merging
- No force-pushes, no branch deletion

`main` additionally requires the `Branch guard` check (rejects any PR whose
source branch isn't `release/*` or `hotfix/*`).

Required approving reviews: 0 (solo maintainer) — revisit this once there's
more than one contributor; the PR-required rule is what actually matters
today, not the approval count.

## Tags

Tags are `vMAJOR.MINOR.PATCH` (semver), created only by the `Release`
workflow from `package.json`'s `version` field when it changes on `main` —
never created by hand, so the tag and the shipped code can't drift apart.

## Deployment

Vercel's native Git integration (Vercel + Neon, ADR-0008) — Production
Branch is `main`, so pushes there (i.e., a `release/*`/`hotfix/*` merge)
auto-deploy to production; every other branch/PR gets a Preview deployment.
No deploy step lives in these workflows today. Full setup and the plan for
later gating production behind the `v*` tag `Release` creates instead:
`docs/DEPLOYMENT.md`.
