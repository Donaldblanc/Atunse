# 0010. Mail-in: capture and validate shipping address only; label generation deferred

## Status
Accepted

## Context
Mail-in Items need a shipping address from the customer. A full mail-in
flow could also generate a prepaid shipping label via a carrier/label API
(e.g. Shippo, EasyPost, USPS/UPS/FedEx directly) — but no such integration
exists yet, and the owner wants the option to add one later without this
being a blocker now.

## Decision
For MVP, mail-in Items only **capture and validate** the shipping address
(address/maps validation — e.g. Google Maps Places/Address Validation API
or a similar service, confirming the address is real and deliverable, not
just non-empty). No label is generated by the app; the actual mail-in
logistics (how the customer ships their sneakers to the shop) happen
outside the app for now.

Address validation is a third-party service and sits behind an adapter per
ADR-0003, the same pattern as storage (ADR-0004) and notifications
(ADR-0006) — so swapping the validation provider, or later adding a real
label-generation adapter (e.g. Shippo/EasyPost) alongside it, doesn't touch
use-case code.

## Consequences
- Smaller scope now — no carrier account, no label-cost handling, no return-shipping logistics to build.
- The customer still has to arrange their own shipping to the shop for a mail-in Item; the app only confirms their address is valid and stores it.
- Adding real label generation later is additive: a new adapter implementation behind the same seam, plus whatever new fields (tracking number, label cost) the Item needs — not a redesign of the mail-in flow itself.
- Tracked as a future feature, not a current TODO blocker — added to docs/TODO.md for visibility.
